# @monodump/react-native-image-gen

Nitro module wrapping Apple's Core ML Stable Diffusion pipeline
([`apple/ml-stable-diffusion`](https://github.com/apple/ml-stable-diffusion))
for on-device image generation in `apps/offline-ai`.

**iOS only.** There is no Android implementation — `nitro.json` declares no
`android` platform, so this HybridObject is never registered on Android at
all. Callers must guard with `Platform.OS === 'ios'` (the app's
`ImageGenService` already does this) rather than relying on a native throw.

## One-time setup after `pnpm install`

`nitrogen/generated/` (the C++/Swift bridge code) is gitignored — it's a
build artifact, regenerated from `src/ImageGen.nitro.ts`, not committed. This
is a **required step before `pod install`**, every time you clone or when the
directory is missing/stale — `pod install` will fail (originally with a
confusing `'functional' file not found` compile error, not an obvious
"missing file" one) if you skip it:

```sh
pnpm --filter @monodump/react-native-image-gen codegen
```

Re-run it any time you edit `src/ImageGen.nitro.ts`.

1. **Run codegen** (above).
2. **Install the `cocoapods-spm` gem** (once per machine/CI image) and use it for `pod install`:
   ```sh
   cd apps/offline-ai && bundle install && cd ios && bundle exec pod install
   ```
   `cocoapods-spm` is what lets `ReactNativeImageGen.podspec` declare
   `s.spm_dependency "stable-diffusion/StableDiffusion"` — Apple only ships
   `ml-stable-diffusion` via Swift Package Manager, with no published
   podspec, so a plain `s.dependency` can't resolve it, and a CocoaPods
   podspec has no built-in way to declare an SPM dependency for its own
   target on its own. See `apps/offline-ai/Gemfile`.

Since `ios/` is gitignored and regenerated by `expo prebuild` (see
`apps/offline-ai/.gitignore`'s "generated native folders" section), the
Podfile lines `cocoapods-spm` needs (`plugin 'cocoapods-spm'` and the
matching `spm_pkg "stable-diffusion", :git => ...`) can't just be hand-edited
into `ios/Podfile` — that edit would be silently lost on the next
`expo prebuild`. They're re-applied automatically on every prebuild by the
Expo config plugin at `apps/offline-ai/plugins/withStableDiffusionSpmPackage.js`
(registered in `app.json`'s `expo.plugins`), which is the part that's
actually checked into git and persists. If you ever need to do this by hand
instead (not using `expo prebuild`), add those same two lines directly to
`ios/Podfile`.

**Gotcha:** the `"stable-diffusion"` identifier in both `spm_pkg` and
`spm_dependency` must exactly match the `name:` Apple's own `Package.swift`
declares (verified via `swift package dump-package`) — it is *not* an
arbitrary label, and it doesn't match the repo name (`ml-stable-diffusion`)
either. Get it wrong and `pod install` fails late, with a confusing
`Package description of '<name>' does not exist!` error rather than an
obvious naming-mismatch one — see `cocoapods-spm`'s
`lib/cocoapods-spm/swift/package/project_packages.rb`.

## Model resources layout

`loadModel(resourcesPath)` expects `resourcesPath` to be a local directory
containing the *compiled* Core ML bundles directly (no zip, no nesting):

```
<resourcesPath>/
  SafetyChecker.mlmodelc/
  TextEncoder.mlmodelc/
  Unet.mlmodelc/            (or UnetChunk1.mlmodelc/ + UnetChunk2.mlmodelc/)
  VAEDecoder.mlmodelc/
  VAEEncoder.mlmodelc/
  vocab.json
  merges.txt
```

This is exactly what `apps/offline-ai/src/services/ImageModelDownloadService.ts`
downloads (file-by-file, preserving the HuggingFace repo's directory
structure) from the curated variants in
`apps/offline-ai/src/types/imageModel.ts` — see those for which HF repos and
paths are used. `StableDiffusionPipeline` auto-detects the chunked-Unet
layout over the single `Unet.mlmodelc` when both `UnetChunk1.mlmodelc` and
`UnetChunk2.mlmodelc` are present, which is what the non-palettized variant
downloads (lower peak memory during load on a phone).

## Why a Nitro module instead of a plain Turbo/legacy native module

Generation runs a ~20-step denoising loop that needs to push a preview frame
back to JS every few steps without the old bridge's JSON-serialize-everything
overhead — Nitro's JSI bindings let `onProgress` be called directly as a JS
function from Swift on the calling thread, not through an async bridge
message queue. That's the actual perf win here: it's not that Core ML
inference itself gets faster, it's that the progress-preview UX (the thing
that keeps generation from *feeling* frozen) doesn't add its own overhead.
